# 🎯 07 — Evaluation: recall@k and IoU

**How the grader decides whether your search found the right place**

`📚 Concepts` · `⏱️ ~20 min read` · `🎯 Prerequisite: 01 — The corpus and character offsets`

</div>

---

> [!IMPORTANT]
> **TL;DR** — The moulinette grades **retrieval only**. For each question, the dataset lists one or more **reference sources** (the "right answers"). A reference counts as **found** if one of your top-*k* results:
> 1. 📁 is in the **same file**, and
> 2. 🔢 overlaps its character range with an **IoU above 0.05**.
>
> **Recall@k** is the share of a question's references found in your top *k*, averaged over all questions. To pass: **≥ 80 %** recall@5 on docs questions, **≥ 50 %** on code questions. 🏁

## 🧪 1. What exactly is graded

During the defense, the pipeline runs as one automated flow:

```text
index ──► search_dataset ──► 🤖 moulinette evaluate_student_search_results
                                   │
                                   ├── 1. validate your JSON
                                   └── 2. compute Recall@1, @3, @5, @10
```

The moulinette compares **two files**:

| File | Comes from | Contains |
|---|---|---|
| 📤 Your search results | `search_dataset` (a `StudentSearchResults` JSON) | For each question: your ranked `retrieved_sources` |
| 📚 Ground truth | `data/datasets/AnsweredQuestions/…` | For each question: its reference `sources` (and an answer) |

> [!NOTE]
> 🙈 Answers generated by Qwen are **not** part of this score. The moulinette's answer evaluation isn't implemented. Answer quality is judged by your peer evaluator (doc 08). The thresholds are about **retrieval**.

| Dataset | Metric | Threshold |
|---|---|:-:|
| 📝 Docs | Recall@5 | **≥ 80 %** |
| 💻 Code | Recall@5 | **≥ 50 %** |

## 📏 2. IoU: measuring overlap between two ranges

**IoU** (**Intersection over Union**, also called the **Jaccard index**) answers: *how much do these two ranges have in common, relative to how much ground they cover together?*

```text
               intersection length
IoU  =  ──────────────────────────────
                union length
```

For two character ranges in the **same file**:

```text
reference:      [────────────]
yours:                [──────────────]
                      ├──────┤            intersection: the shared part
                ├────────────────────┤    union: from the leftmost start to the rightmost end
```

| IoU | Meaning |
|:-:|---|
| **0** | No shared character at all |
| **1** | Exactly the same range |
| in between | Partial overlap, or one range inside the other |

### 🧮 Examples

Reference: **[1000 : 1200]** (200 characters)

| Your range | Situation | Intersection | Union | IoU | Found? |
|---|---|:-:|:-:|:-:|:-:|
| [1000 : 1200] | 🎯 Identical | 200 | 200 | **1.000** | ✅ |
| [900 : 1150] | Partial, similar size | 150 | 300 | **0.500** | ✅ |
| [1100 : 1300] | Partial, similar size | 100 | 300 | **0.333** | ✅ |
| [0 : 2000] | Contains it, 10× wider | 200 | 2000 | **0.100** | ✅ |
| [1150 : 3150] | Barely touches, much wider | 50 | 2150 | **0.023** | ❌ |
| [1300 : 2000] | No overlap | 0 | — | **0** | ❌ |
| [1000 : 1200] in **another file** | Wrong file | — | — | — | ❌ |

> [!IMPORTANT]
> 📁 The file check comes **first**. A perfect range in the wrong file is worth nothing, and so is a path that differs by a single character (doc 01, Section 7).

## 🤏 3. Why 0.05 is a permissive bar (and where it bites)

### ✅ Permissive

An IoU of 0.05 means only **5 %** of the combined span needs to be shared. In practice:

- you **don't** need to match the reference's boundaries;
- a chunk that **contains** the reference counts even if it's up to **20× wider**;
- a chunk that **partially** overlaps a similarly sized reference counts easily.

The bar is low on purpose: it rewards finding **the right region of the right file**, not guessing the exact span the dataset author highlighted. 🎯

### ❌ Where it still bites

Doc 02 showed the catch: when your chunk **contains** the reference,

```text
IoU = reference width ÷ chunk width
```

| Reference width | Max chunk width that can still count |
|:-:|:-:|
| 400 | 8000 (but you're capped at 2000 anyway) |
| 200 | 4000 |
| 100 | 2000 |
| 50 | 1000 |
| 20 | 400 |

<sub>These are the exact break-even widths (IoU = 0.05). Aim comfortably below them, don't design for the edge.</sub>

And for **partial** overlap with a big chunk, it bites even harder: [1150 : 3150] touched the reference but scored 0.023.

> [!TIP]
> 📐 So "permissive" depends on **your chunk sizes** relative to the **reference widths**. How wide are the references in the real datasets? Measure them (doc 01, Section 9). That single number tells you how much room your chunk size has. 🔬

## 🔢 4. Recall@k

### 📌 For one question

```text
                  number of the question's references found in your top k
recall@k(q) =  ───────────────────────────────────────────────────────────────
                       number of the question's references
```

- Only your **first k** results are looked at. Results 6–10 don't help recall@5.
- **Wrong** results in the top k aren't penalised directly… but they take up slots. 🪑

### 📊 For a dataset

The per-question values are **averaged** over all questions. That's the number the moulinette prints as `Recall@5: 0.880 (88.0 %)`.

> [!NOTE]
> ⚖️ Averaging per question means every question weighs the same: a question with 1 reference counts as much as one with 4. Missing the single reference of an easy question costs a full "1.0" for that question.

### 🔁 Several k at once

The moulinette reports **@1, @3, @5, @10**. Only @5 is graded, but the others tell a story:

| Pattern | What it suggests |
|---|---|
| @1 low, @5 high | You **find** the right chunks but rank them too low. Ranking (doc 05) can improve |
| @5 ≈ @10, both low | The right chunks are **not found at all**. Look at chunking, tokenization, files indexed |
| @10 much higher than @5 | Close to the threshold: small ranking improvements may push them into the top 5 |

## ✏️ 5. Worked example: one question, then a dataset

### ❓ Question Q1 has two references

| Ref | file_path | Range |
|:-:|---|---|
| R1 | `docs/a.md` | [1000 : 1200] |
| R2 | `vllm/b.py` | [500 : 900] |

<sub>Paths shortened: in reality they all start with `data/raw/vllm-0.10.1/`.</sub>

### 📤 Your top-5 results

| Rank | file_path | Range | Matches R1? | Matches R2? |
|:-:|---|---|:-:|:-:|
| 1 | `docs/a.md` | [0 : 2000] | ✅ IoU 0.10 | — |
| 2 | `docs/c.md` | [0 : 1500] | — | — |
| 3 | `vllm/b.py` | [3000 : 4000] | — | ❌ same file, no overlap |
| 4 | `vllm/b.py` | [400 : 1400] | — | ✅ IoU 0.40 |
| 5 | `docs/a.md` | [1800 : 3800] | ❌ no overlap | — |

### 🔢 Recall for Q1

| k | Results considered | References found | **recall@k** |
|:-:|---|---|:-:|
| 1 | rank 1 | R1 | 1 / 2 = **0.5** |
| 3 | ranks 1–3 | R1 | 1 / 2 = **0.5** |
| 5 | ranks 1–5 | R1, R2 | 2 / 2 = **1.0** |

👀 R2 was found only at rank **4**. With a slightly worse ranking (rank 6), recall@5 for Q1 would have been 0.5.

### 📊 A tiny dataset of three questions

| Question | References | Found in top 5 | recall@5 |
|:-:|:-:|:-:|:-:|
| Q1 | 2 | 2 | 1.0 |
| Q2 | 1 | 1 | 1.0 |
| Q3 | 1 | 0 | 0.0 |
| | | **Average** | **0.667** (66.7 %) |

> [!TIP]
> 🎯 For the docs threshold (80 %), you can afford to completely miss only about **1 question in 5**. For code (50 %), about **half**. That's why the code threshold is lower: code questions are much harder for lexical search (doc 03, vocabulary mismatch).

## 🤔 6. Why recall, and not something else?

| Metric | Measures | Fits this project? |
|---|---|---|
| 🎯 **Recall@k** | Did the right sources make it into the top k? | ✅ The LLM reads exactly the top-k. If the source isn't there, the answer can't be grounded |
| 🧹 **Precision@k** | What fraction of the top k is relevant? | Partially: junk in the context confuses the model, but with 1–2 references per question precision is always low |
| 🥇 **MRR** (Mean Reciprocal Rank) | How high is the **first** right result? | Interesting for ranking quality, not graded |
| 📈 **nDCG** | Rewards relevant results more when they're higher | Common in research, not graded |

> [!NOTE]
> 🧠 Recall@k matches the RAG pipeline's real need (doc 00): **the generator can only use what retrieval puts in front of it**. A missing source is a hard failure. An extra irrelevant source is a softer one.

> [!TIP]
> 📝 The README's "Performance analysis" section can go beyond the required numbers: recall at several k, docs vs code, the effect of chunk size… and why your system behaves that way.

## 🚫 7. Validation: when the whole file is rejected

Before computing anything, the moulinette checks your file (`Student data is valid: True`). If validation fails, **nothing** is scored. 💥

| Check | What fails it |
|---|---|
| 🧾 **Format** | JSON not matching `StudentSearchResults`: missing fields, wrong types, malformed JSON |
| 📏 **Source width** | Any source wider than `--max_context_length` (2000): **one** is enough |
| 🔢 **Number of sources** | More sources per question than `--k` |
| 🆔 **Questions** | Question IDs that don't correspond to the dataset (the output reports how many questions have student sources) |

> [!CAUTION]
> 💣 Validation errors are **all-or-nothing**. One over-long chunk among thousands of results, one bad field, and the score is gone. Your pydantic models (doc 09) and the chunking invariants (doc 02, Section 9) are your shield. 🛡️

> [!WARNING]
> 🆔 Keep each question's `question_id` **exactly** as in the input dataset. If your output invents new IDs (for example, a default UUID generated because the field wasn't copied), your results can't be matched to the ground truth.

## 🛠️ 8. Your own `evaluate` command

The subject requires an `evaluate` command:

```text
uv run python -m src evaluate --student_search_results_path <path> --dataset_path <path>
```

| Rule | From the subject |
|---|---|
| 🧪 Purpose | For **your own iteration** |
| 🚫 Moulinette | Your solution must **never import or call** it |
| 🏛️ Official score | Computed by the moulinette at the defense, not by your code |

### 💡 What makes your own evaluator worth more than the moulinette

The moulinette gives you **four numbers**. Your evaluator can give you **why**:

| Feature | Helps you… |
|---|---|
| 📋 Per-question results | See **which** questions fail |
| 📁 "Right file, wrong region" vs "file not found" | Distinguish a chunking problem from a search problem |
| 📏 The IoU of the best attempt per reference | Spot near-misses (e.g. 0.04 instead of 0.05) |
| 🔀 Separate docs / code reports | See which strategy needs work |

> [!TIP]
> 🧮 Check that your evaluator agrees with the moulinette on the same files. If both say 0.86 on docs, you can trust yours for fast experiments. If they disagree, one of you has a different definition (threshold, averaging…), and finding out which is a great way to really understand the metric. 🕵️

## 🔬 9. Failure analysis: turning a low score into a fix

When a question fails, put **the reference** and **your top results** side by side. Most failures fall into a few categories:

| Symptom | Likely cause | Look at |
|---|---|---|
| 💀 **Every** question fails, recall ≈ 0 | `file_path` format, offsets convention, wrong corpus path | Doc 01 |
| 📂 The reference's **file** never appears in your results | The file isn't indexed, or its terms don't match the question | Doc 01 §1 (files indexed) · Doc 03 (tokenization) |
| 📁 Right file, **wrong region** | The relevant part is buried in a chunk dominated by other content, or chunk boundaries split it | Doc 02 (chunking) |
| 📏 Right region, but **IoU < 0.05** | Chunk too big for a narrow reference, or barely overlapping it | Doc 02 §3 (IoU ceiling) |
| 🥈 Right chunk exists but ranked **6th–10th** | Ranking: other chunks win on common terms or length | Doc 05 (BM25 parameters) · Doc 03 (stopwords, identifiers) |
| 🗣️ Question and reference share **no words** | Vocabulary mismatch | Doc 03 §9 · semantic bonus (doc 11) |
| 👯 Top 5 contains near-duplicates of the same place | Overlap or similar neighbouring chunks waste slots | Doc 02 §4 |

> [!TIP]
> 🗂️ Look at **10–20 failing questions** by hand, categorise them, and count. "12 of 20 failures are *right file, wrong region*" tells you exactly where to spend your next hour. Guessing doesn't. 🎯

## 🚫 10. Common misconceptions

| ❌ Myth | ✅ Reality |
|---|---|
| "I need to match the reference range exactly." | An IoU above 0.05 is enough. The right region of the right file is what counts. |
| "If my chunk overlaps the reference, it counts." | Only if the **ratio** of shared to combined length is above 0.05. Big chunks barely touching don't count. |
| "Wrong results in the top 5 lower my score." | Not directly: recall ignores them. They only cost by taking slots. |
| "Recall@10 is what matters." | Only **@5** is graded. @1/@3/@10 are diagnostics. |
| "The moulinette grades my answers too." | It grades **retrieval**. Answers are judged by the evaluator. |
| "One bad source only costs one question." | A validation error (e.g. one source > 2000 chars) invalidates the **whole file**. |
| "My `evaluate` can just call the moulinette." | The subject forbids importing or calling it. |
| "Ranking order doesn't matter for recall." | It matters at the cut-off: rank 5 counts for @5, rank 6 doesn't. |
