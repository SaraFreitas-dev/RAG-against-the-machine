# 🏆 05 — BM25

**A practical guide to term saturation and document-length normalization**

`📚 Concepts` · `⏱️ ~25 min read` · `🎯 Prerequisite: 04 — TF-IDF`

</div>

---

> [!IMPORTANT]

> _**TL;DR**_ — _**BM25**_ (Best Matching 25) keeps TF-IDF's core idea, *rare terms that appear in a chunk are strong evidence*, and fixes its two biggest weaknesses with two parameters:_

> - 🔁 **`k1`** controls **saturation**: how quickly repeating a term stops adding to the score;

> - 📏 **`b`** controls **length normalization**: how much a chunk is penalised for being longer than average.


> BM25 has served as a standard baseline for lexical search for decades. It is one of the retrieval methods accepted by the project specification and is suitable for corpora with uneven chunk lengths. 🎯

## 🔙 1. What TF-IDF left unsolved

From doc 04, Section 10:

| Problem | TF-IDF's answer | Why it's not enough |

|---|---|---|

| 🔁 Repeating a word 100× shouldn't count 100× | Log-TF, sometimes | Fixed curve, nothing to tune |

| 📏 Long chunks contain more terms just by being long | Cosine normalization, sometimes | All-or-nothing, can over- or under-punish |

| 🎛️ Results are off | — | No knobs to turn |

BM25 answers all three in **one formula** with **two knobs**. 🎛️🎛️

---

## Foundations: how indexing and searching fit together

BM25 is a **lexical ranking algorithm**: it scores a document based on the words it shares with a query. In this RAG project, **one chunk is one document** for BM25. A file can produce several chunks, and each chunk is counted separately.

The work happens in two distinct stages:

| Stage | What happens | Output |
|---|---|---|
| **Indexing** | Read documents, tokenize their text, count terms, compute corpus statistics | Data needed to score future queries |
| **Searching** | Tokenize a query, calculate BM25 scores using those statistics, rank matching documents | The most relevant chunks |

**Important:** building an index does **not** mean computing a BM25 score for every possible question. The question only arrives later, at search time.

### A tiny example of tokenization

Term counting first requires representing text as individual terms (tokens). The following is a deliberately simple **illustrative example**, not a production tokenizer:

```python
sentence = "GPU memory memory cache"
tokens = sentence.lower().split()

print(tokens)
# ['gpu', 'memory', 'memory', 'cache']
```

This example does not handle punctuation or Python identifiers. A real code-search tokenizer must decide how to treat names such as `gpu_memory_utilization`; that is a separate design decision.

## Foundations: TF, DF, N and IDF

The following three short documents (chunks) illustrate four related concepts:

| Chunk | Tokenized content |
|---|---|
| **A** | `memory memory gpu` |
| **B** | `memory worker` |
| **C** | `gpu cache` |

### TF — term frequency (within **one** chunk)

**TF(t, d)** means *the number of occurrences of term `t` in document `d`*.

For the term `memory`:

| Chunk | TF of `memory` |
|---|---:|
| A | 2 |
| B | 1 |
| C | 0 |

A small Python illustration:

```python
from collections import Counter

tokens = ["memory", "memory", "gpu"]
frequencies = Counter(tokens)

print(frequencies["memory"])  # 2
print(frequencies["gpu"])     # 1
```

This counts occurrences **inside one list of tokens**. It does not calculate BM25.

### DF — document frequency (across **different** chunks)

**DF(t)** means *the number of distinct documents containing `t` at least once*.

Here, `memory` occurs in **A and B**, so **DF(memory) = 2**. It appears three times in total, but DF is **not 3**. Similarly, **DF(gpu) = 2** and **DF(cache) = 1**.

A Python illustration of the **idea of distinct documents**, using a completely separate toy dataset:

```python
documents = [
    ["red", "red", "blue"],
    ["red", "green"],
    ["blue", "yellow"],
]

term = "red"
documents_containing_term = sum(term in doc for doc in documents)
print(documents_containing_term)  # 2, not 3
```

Notice that `term in doc` produces a boolean: each document contributes either **1 or 0**, regardless of how often the term repeats.

### N — corpus size

**N** is the total number of indexed documents. In the example, **N = 3**. When chunks are used as BM25 documents, N counts **chunks**, not source files.

### IDF — inverse document frequency (how discriminative is a term?)

**IDF(t)** is calculated from **N** and **DF(t)**. It gives more weight to rarer terms because they tend to distinguish relevant documents better:

- `cache`: DF = 1 → rarer → higher IDF.
- `memory`: DF = 2 → more common → lower IDF.

**TF and DF describe different things:** TF asks *“How often in this chunk?”*; DF asks *“In how many chunks?”*; IDF turns the second answer into a rarity weight.

#### Worked check

Suppose the term `worker` occurs five times in chunk A, once in chunk B, and nowhere else among 50 chunks. Then **TF(worker, A) = 5**, **DF(worker) = 2**, and **N = 50**. The total of six occurrences must **not** be mistaken for DF.

Once those quantities are clear, the BM25 formula below is just a way to combine **rarity**, **repetition with diminishing returns**, and **document-length normalization**.

## 🧮 2. The formula, at a glance

For a question **q** and a chunk **d**:

```text

                          tf(t,d) · (k1 + 1)

score(q,d) =  Σ  idf(t) · ─────────────────────────────────────

             t∈q          tf(t,d) + k1 · (1 − b + b · |d| / avgdl)

```

Although the BM25 formula may appear complex at first, it combines three fundamental concepts: term rarity, term-frequency saturation, and document-length normalization:

| Piece | Symbol(s) | Idea | Section |

|---|---|---|:-:|

| 💎 **Rarity** | `idf(t)` | Rare terms are strong clues (like TF-IDF) | 3 |

| 🔁 **Saturation** | `tf`, `k1` | Repetitions help, with diminishing returns | 4 |

| 📏 **Length** | `\\|d\\|`, `avgdl`, `b` | Longer-than-average chunks get their TF discounted | 5 |

| Symbol | Meaning |

|---|---|

| `tf(t,d)` | Occurrences of term **t** in chunk **d** (doc 04) |

| `\\|d\\|` | Length of chunk **d**, **in terms** (after tokenization), not characters |

| `avgdl` | Average chunk length over the whole index, in terms |

| `k1` | Saturation parameter, usually between **1.2 and 2.0** |

| `b` | Length-normalization parameter, between **0 and 1**, usually **0.75** |

> [!NOTE]

> 🧮 Like TF-IDF, only terms present in _**both**_ the question and the chunk contribute. A chunk sharing no term with the question scores 0._

## 💎 3. Piece 1: IDF, BM25-style

BM25 usually uses a slightly different IDF, coming from probability theory (the "Robertson–Spärck Jones" weight):

```text

              ⎛  N − df(t) + 0.5      ⎞

idf(t) =  ln  ⎜ ───────────────── + 1 ⎟

              ⎝    df(t) + 0.5        ⎠

```

| Part | Why it's there |

|---|---|

| `N − df` vs `df` | Compares chunks **without** the term to chunks **with** it |

| `+ 0.5` | Smoothing: avoids division by zero and extreme values |

| `+ 1` inside the log | Keeps the IDF **positive** even for terms in almost every chunk |

**### 🤔 Why does the `+ 1` matter?**

The original formula, without `+ 1`, gives **negative** weights to terms that appear in more than half the chunks. With N = 4 and a term in all 4 chunks:

| Version | Value | Effect |

|---|:-:|---|

| Without `+ 1`: `ln(0.5 / 4.5)` | **−2.197** | 😱 Matching the term **lowers** the score |

| With `+ 1`: `ln(0.5 / 4.5 + 1)` | **0.105** | 🤏 Tiny positive weight, as intended |

> [!TIP]

> 🐍 In code, "terms in more than half the chunks" isn't hypothetical: `self`, `def`, `return`, `import`… The selected IDF variant determines how these frequent terms affect ranking. 🔍*

---

## 🔁 4. Piece 2: saturation and `k1`

Ignore length for a moment (pretend every chunk has average length, or `b = 0`). The TF part becomes:

```text

     tf · (k1 + 1)

    ───────────────

       tf + k1

```

**### 📈 What this curve does**

| tf → | 1 | 2 | 3 | 5 | 10 | 100 | **Limit** |

|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|

| `k1 = 0` | 1.00 | 1.00 | 1.00 | 1.00 | 1.00 | 1.00 | **1** |

| `k1 = 0.5` | 1.00 | 1.20 | 1.29 | 1.36 | 1.43 | 1.49 | **1.5** |

| `k1 = 1.2` | 1.00 | 1.38 | 1.57 | 1.77 | 1.96 | 2.17 | **2.2** |

| `k1 = 2.0` | 1.00 | 1.50 | 1.80 | 2.14 | 2.50 | 2.94 | **3** |

| `k1 = 10` | 1.00 | 1.83 | 2.54 | 3.67 | 5.50 | 10.0 | **11** |

**### 🔍 Reading the table**

| Observation | Meaning |

|---|---|

| 🎯 `tf = 1` always gives **1.00** | The first occurrence is worth the same whatever `k1` is |

| 🧱 There's a **ceiling** at `k1 + 1` | No amount of repetition can push past it: this is **saturation** |

| `k1 = 0` | Only presence matters: "does the chunk contain the term, yes or no" |

| Small `k1` | Saturates fast: the 2nd and 3rd occurrences add little |

| Large `k1` | Saturates slowly: behaves almost like raw TF |

> [!IMPORTANT]

> 🎛️ _**`k1` answers one question:**_ *how much should repeating a term matter?* With the usual values (1.2–2.0), going from 1 to 2 occurrences helps a lot, and going from 10 to 100 barely helps._

---

## 📏 5. Piece 3: length normalization and `b`

**### 🤔 The problem**

A 1900-character chunk contains many more terms than a 200-character one. So it's more likely to contain the question's terms, and to contain them several times, **just by being long**, not because it's more relevant.

**### 🔧 The fix**

BM25 replaces `k1` in the denominator with an adjusted value, here called **K**:

```text

K = k1 · (1 − b + b · |d| / avgdl)

```

The ratio `|d| / avgdl` compares this chunk's length to the average:

| Chunk length | `\\|d\\| / avgdl` | Effect on K (when b > 0) | Effect on score |

|---|:-:|---|---|

| Shorter than average | < 1 | K **smaller** | TF counts **more** 📈 |

| Exactly average | = 1 | K = k1 | Neutral |

| Longer than average | > 1 | K **bigger** | TF counts **less** 📉 |

**### 🎚️ What `b` controls**

`b` decides **how much** length matters, from 0 to 1:

| `b` | Formula becomes | Meaning |

|:-:|---|---|

| **0** | K = k1 | 🙈 Length ignored completely |

| **0.75** | mostly the length ratio | ⚖️ The usual default: strong but partial normalization |

| **1** | K = k1 · \\|d\\| / avgdl | 📏 Full normalization: TF is effectively measured relative to length |

**### 🧮 Example: same tf, different lengths**

Term appearing **twice** (`tf = 2`), `k1 = 1.2`. TF-part value depending on chunk length:

| `b` ↓ / length → | ½ × avg | 1 × avg | 2 × avg | 4 × avg |

|:-:|:-:|:-:|:-:|:-:|

| **0** | 1.38 | 1.38 | 1.38 | 1.38 |

| **0.5** | 1.52 | 1.38 | 1.16 | 0.88 |

| **0.75** | 1.60 | 1.38 | 1.07 | 0.75 |

| **1.0** | 1.69 | 1.38 | 1.00 | 0.65 |

👀 With `b = 0.75`, a chunk **4× longer** than average gets about **half** the credit for the same two occurrences, compared with an average chunk.

> [!NOTE]

> 🧭 Length normalization interacts _**directly**_ with chunking (doc 02). When a chunking strategy produces a mix of short sections and near-2000-character functions, `b` determines how strongly those length differences affect ranking. 📐_

## ✏️ 6. Worked example, by hand

Same tiny index as in doc 04, with `k1 = 1.2` and `b = 0.75`:

| Chunk | Terms | \\|d\\| |

|:-:|---|:-:|

| C1 | port · server · port · default | 4 |

| C2 | server · start · model | 3 |

| C3 | model · config · port | 3 |

| C4 | model · load · model · weights | 4 |

`N = 4` · `avgdl = (4 + 3 + 3 + 4) / 4 = 3.5`

**### 1️⃣ IDF (BM25-style)**

| Term | df | Computation | **idf** |

|---|:-:|---|:-:|

| default | 1 | ln((4 − 1 + 0.5) / (1 + 0.5) + 1) = ln(3.333) | **1.204** |

| port | 2 | ln((4 − 2 + 0.5) / (2 + 0.5) + 1) = ln(2) | **0.693** |

**### 2️⃣ Length factor K for each matching chunk**

| Chunk | \\|d\\| / avgdl | K = 1.2 · (0.25 + 0.75 · ratio) |

|:-:|:-:|:-:|

| C1 | 4 / 3.5 = 1.143 | **1.329** |

| C3 | 3 / 3.5 = 0.857 | **1.071** |

**### 3️⃣ Score the question **_*"default port"*_

| Chunk | Term | tf | idf × tf·(k1+1) / (tf + K) | Contribution |

|:-:|---|:-:|---|:-:|

| C1 | default | 1 | 1.204 × 2.2 / 2.329 | 1.137 |

| C1 | port | 2 | 0.693 × 4.4 / 3.329 | 0.916 |

| | | | **C1 total** | **2.054** 🥇 |

| C3 | port | 1 | 0.693 × 2.2 / 2.071 | **0.736** 🥈 |

| C2, C4 | — | 0 | — | **0** |

**Ranking:** C1 → C3 → (C2, C4). Same order as TF-IDF here: on a clean example, both agree. ✅ The difference shows up on **messy** data. 👇

## 😈 7. The repetition chunk, revisited

Add doc 04's silly chunk again:

```text

C5: port port port port port port port port port port     (10 × "port", |d| = 10)

```

Now `N = 5`, `avgdl = 4.8`, `idf(port) = 0.539`, `idf(default) = 1.386`.

| Chunk | TF-IDF, raw TF (doc 04) | TF-IDF, log TF (doc 04) | **BM25** (`k1 = 1.2`, `b = 0.75`) |

|:-:|:-:|:-:|:-:|

| C1 (the real answer) | 2.631 | 2.474 🥇 | **2.265** 🥇 |

| C5 (spam) | 5.108 🥇 😱 | 1.687 | **0.974** |

Why BM25 crushes C5:

| Effect | On C5 |

|---|---|

| 🔁 **Saturation** | 10 occurrences ≈ only ~2× the value of one, never more than `k1 + 1 = 2.2` |

| 📏 **Length** | C5 is twice the average length, so K grows to **2.175** and the TF part shrinks further |

> [!IMPORTANT]

> 🎯 This is the core of BM25's advantage: _**both**_ mechanisms push the same way against chunks that score high only by being long or repetitive. In a real corpus that means large boilerplate code files, long tables, or lists. 📋_

## 🎛️ 8. Tuning `k1` and `b`

**### 📍 Starting point**

The classic defaults, **`k1 ≈ 1.2–2.0`** and **`b = 0.75`**, come from decades of experiments on **English prose** (news, web pages). A mixed corpus of code and documentation may have highly uneven chunk lengths. The defaults are a reasonable start, not a guarantee. 🤷

**### 🔬 How to tune**

1. 🎛️ Pick a small grid, e.g. `k1 ∈ {0.9, 1.2, 1.5, 2.0}` × `b ∈ {0.3, 0.5, 0.75, 0.9}`.

2. 🔁 For each pair, run `search_dataset` and evaluate recall\@5.

3. 📊 Look at **docs and code separately**: they may prefer different values.

4. 📝 Record the results in a performance-analysis section.

> [!TIP]

> ⚡ Changing `k1` or `b` doesn't require re-chunking or re-tokenizing. Whether it requires rebuilding an index depends on the stored structures (doc 06). Slow tuning may indicate opportunities to improve the index design. 🧩_

**### ⚠️ Overfitting**

> [!WARNING]

> 🎯 Extensive tuning on _**public**_ datasets may cause overfitting to those questions. Reference evaluation questions may differ. Prefer settings that perform _**consistently across both**_ datasets rather than optimizing only one. Big gains from tuning usually mean something else (chunking, tokenization) deserves attention. 🔍_

## 🔗 9. How BM25 interacts with preprocessing choices

BM25 doesn't work in isolation. Choices from earlier docs change its inputs:

| Earlier choice | Affects | How |

|---|---|---|

| ✂️ **Chunk size** (doc 02) | `\\|d\\|`, `avgdl` | Changes what "long" means, and how much `b` matters |

| 🔁 **Overlap** (doc 02) | `tf`, `df` | Shared text is counted in several chunks: `df` grows for those terms |

| 🔤 **Emitting identifier parts** (doc 03) | `tf`, `\\|d\\|` | `max_num_seqs` → 4 terms: code chunks get longer in terms, and `max` gets extra occurrences |

| 🚮 **Stopwords** (doc 03) | `\\|d\\|`, `avgdl` | Removing them shortens every chunk |

| 🧭 **Extra context in indexed text** (doc 02, Section 8) | `tf`, `\\|d\\|` | Adding a heading or file name to each chunk adds terms and length |

> [!NOTE]

> 🔬 That's why "change one thing at a time" (doc 02, Section 10) matters: a tokenizer change can shift the best `b` value, because it changes chunk lengths.*

**### ❓ Repeated words in the question**

If a question repeats a term (**"port … which port …"**), should it count twice? The basic formula sums over **query terms**, so the result depends on whether the query is treated as a list (repetitions count) or a set (each term once). Some BM25 variants add a third parameter for this. Because queries are often short, the effect may be limited; nevertheless, the handling of duplicate terms should be explicit. 🤔

## 🧩 10. Variants and libraries

"BM25" is also a small family:

| Variant | Difference |

|---|---|

| **Okapi BM25** | The classic formula above (with one of several IDF versions) |

| **BM25+** | Adds a small constant so long chunks containing a term never score **lower** than chunks without it |

| **BM25L** | Adjusts length normalization to penalise long documents less |

| **BM25F** | Weights several fields differently (e.g. title vs body), relevant if you index a heading separately from the text |

> [!WARNING]

> 📚 Libraries exist (for example `rank-bm25` on PyPI), and they differ in _**IDF variant**_, handling of negative IDF, and defaults. When using a library, its documentation or source should be consulted to identify _**exactly**_ which BM25 variant it computes. The project specification requires implementation of TF-IDF or BM25, but does not explicitly clarify whether using an existing implementation is sufficient. An independent implementation can make the scoring mechanics easier to explain during assessment._

## ⚖️ 11. TF-IDF vs BM25

| | 📊 TF-IDF | 🏆 BM25 |

|---|---|---|

| **Rarity** | IDF | IDF (probabilistic variant) |

| **Repetition** | Linear, or log if you choose | Built-in **saturation**, tunable with `k1` |

| **Length** | None, or cosine normalization | Built-in, tunable with `b` |

| **Parameters** | None | `k1`, `b` |

| **Explainability** | ✅ Very simple | ✅ Simple once each piece is understood |

| **Speed** | ⚡ Fast | ⚡ Fast (same counts, a few more operations) |

| **Typical quality** | Good baseline | Usually better, especially with uneven lengths |

| **Shared limits** | Bag of words · exact terms only · no synonyms (doc 03, Section 9) | Same |

## 🚫 12. Common misconceptions

| ❌ Myth | ✅ Reality |

|---|---|

| "BM25 understands meaning better than TF-IDF." | It's still **lexical**: it only sees exact term matches. It just weighs them more sensibly. |

| "`\\|d\\|` is the chunk length in characters." | It's measured in **terms**, after tokenization. |

| "`k1` makes the score bigger or smaller." | It controls how **fast** repetitions saturate. For an average-length chunk (or when `b = 0`), the first occurrence contributes `1 × IDF`; with length normalization enabled, its contribution also depends on chunk length. |

| "`b = 1` is best: full fairness to short chunks." | Full normalization can over-favour tiny chunks with one lucky match. That's why the default is 0.75. |

| "The default parameters are optimal." | They are useful starting points, but performance on mixed code-and-documentation corpora should be measured. |

| "IDF in BM25 can't be negative." | It can, without the `+ 1` term, for terms in more than half the chunks. |

| "Tuning `k1` and `b` is the main lever for recall." | Usually small gains. Chunking and tokenization tend to matter much more. |
