# LangChain Text Splitters

## 1. What is LangChain?

LangChain is a Python ecosystem for building applications that work with language models and external information. **`langchain-text-splitters`** is a separate package dedicated to dividing text into manageable chunks.

In a Retrieval-Augmented Generation (RAG) pipeline, chunking happens before indexing:

```text
Source files → Read text → Split into chunks → Build index → Retrieve → Answer
```

We do **not** need to adopt the entire LangChain framework to use its text splitters.

## 2. Why split documents?

A large file may contain several unrelated functions or documentation sections. Indexing smaller chunks can make retrieval more focused.

A useful chunking strategy should:

- Keep related information together where practical.
- Respect a configured maximum length.
- Preserve enough context for retrieval.
- Retain a traceable reference to the original file.

There is no universally optimal chunk size. It is a parameter to test, not an automatic guarantee of better retrieval.

## 3. `RecursiveCharacterTextSplitter`

`RecursiveCharacterTextSplitter` attempts to split text using a **priority list of separators**. If a piece is too large, it tries finer separators until its pieces can fit within the configured size.

For ordinary text, this often means trying paragraph boundaries, then line boundaries, then spaces, then character-level cuts. The exact separator list can be customized.

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=2000,
    chunk_overlap=15,
    length_function=len,
    add_start_index=True,
    strip_whitespace=False,
)

chunks = splitter.create_documents([text])
```

Here `text` is an existing string holding the source content.

### Main parameters

| Parameter | Purpose |
|---|---|
| `chunk_size` | Maximum target size measured by `length_function`. With `len`, it is Python string characters. |
| `chunk_overlap` | Requested shared context between adjacent chunks, where the splitting/merging strategy permits it. Not guaranteed to be exactly this many characters. |
| `length_function` | Defines how size is measured; `len` counts Python string characters. |
| `add_start_index=True` | Adds a `start_index` to each created `Document`'s metadata. |
| `strip_whitespace=False` | Avoids trimming surrounding whitespace from each resulting chunk. Useful when preserving source text. |
| `separators` | Optional ordered list of boundaries used when splitting. |

**Important:** `chunk_overlap` must be smaller than `chunk_size`. For very small maximum sizes, adjust the overlap accordingly.

## 4. Language-aware splitting

LangChain provides different separator lists for languages, including Python and Markdown:

```python
from langchain_text_splitters import Language, RecursiveCharacterTextSplitter

python_splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.PYTHON,
    chunk_size=2000,
    chunk_overlap=15,
    add_start_index=True,
    strip_whitespace=False,
)

markdown_splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.MARKDOWN,
    chunk_size=2000,
    chunk_overlap=15,
    add_start_index=True,
    strip_whitespace=False,
)
```

Language-aware means **separator-aware**, not syntax-tree-aware:

- For Python, the splitter uses text patterns associated with classes, functions, and other constructs. It does **not** parse a Python AST.
- For Markdown, it prioritizes Markdown-oriented boundaries such as headings.
- Neither mode guarantees that every function, class, or Markdown section will remain complete.

## 5. `split_text()` vs. `create_documents()`

`split_text()` returns strings:

```python
parts: list[str] = python_splitter.split_text(text)
```

`create_documents()` returns LangChain `Document` objects:

```python
documents = python_splitter.create_documents(
    [text],
    metadatas=[{"file_path": "src/example.py"}],
)

for document in documents:
    print(document.page_content)
    print(document.metadata)
```

A `Document` has:

- `page_content`: the chunk text.
- `metadata`: information such as `file_path` and, with `add_start_index=True`, `start_index`.

For this RAG project, these are intermediate objects; the final output should follow our own `Chunk` and `MinimalSource` Pydantic models.

## 6. Offsets: the critical part of our RAG

The project needs source positions that refer to the **original file**, not just to a chunk or a temporary substring.

For a chunk beginning at character `start` and containing `content`:

```python
end = start + len(content)
assert original_text[start:end] == content
```

This uses a half-open interval **`[start, end)`**: `start` is included and `end` is excluded.

### When splitting only part of a file

Suppose AST identifies an oversized Python block from position `500` to `3500`:

```python
section = original_text[500:3500]
```

If the splitter reports a chunk's `start_index` as `120` **within `section`**, its absolute starting position is:

```python
absolute_start = 500 + 120
absolute_end = absolute_start + len(chunk.page_content)
```

The same principle applies to any extracted subsection.

**Never blindly trust offsets from a splitter.** Validate them against the original text, especially when text repeats, overlaps are enabled, or whitespace is transformed. Reject or resolve mismatches instead of silently saving incorrect source positions.

## 7. Our proposed hybrid approach: AST + LangChain

Our Python chunking strategy can combine **structural boundaries** with a library-based fallback for oversized blocks:

```text
Python file
   ↓
AST: identify top-level imports, functions, classes, decorators
   ↓
List of original-file character ranges
   ↓
Does a range exceed max_size?
   ├── No  → Keep the range
   └── Yes → Split that range using LangChain
                 ↓
           Convert local to absolute offsets
   ↓
Validate lengths and source slices
   ↓
Build our own Chunk / MinimalSource objects
```

For Markdown, using `Language.MARKDOWN` directly is a simpler first implementation. We only need custom heading parsing if testing demonstrates a reason for it.

**Trade-off:** LangChain reduces custom splitting code, but AST-based boundaries require extra code and tests. We should keep the hybrid approach only if its structural control is useful.

## 8. Testing checklist

For each generated chunk, verify:

```python
assert 0 <= start < end <= len(original_text)
assert end - start <= max_size
assert original_text[start:end] == chunk_text
```

Also test:

- Empty files.
- Files containing only imports, comments, or constants.
- Python decorators and consecutive imports.
- Long Python classes and functions.
- Markdown headings, lists, and fenced code blocks.
- Repeated text and consecutive identical lines.
- Unicode characters and different newline styles.
- Overlap and very small `max_size` values.
- Invalid Python syntax (the AST fallback should still return usable ranges).

Note: exact source slices do not require every whitespace-only gap to be indexed. Decide explicitly whether those gaps are skipped or retained.

## 9. Installing with `uv`

From the project root:

```bash
uv add langchain-text-splitters
uv sync
```

Only add further LangChain packages when needed. The splitter package is sufficient for the examples in this note.
